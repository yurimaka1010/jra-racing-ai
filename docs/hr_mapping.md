## 状態の定義

| 状態 | 適用条件 |
|---|---|
| confirmed | 対象の意味を仕様で確認し、PC-KEIBAの実構造・変換規則との対応も確認済み |
| proposed | 設計上の提案。実データへの変換規則や確認済み事実ではない |
| needs_confirmation | 仕様版・実列・単位・履歴などの追加確認が必要 |
| prohibited_feature | 予測特徴量への採用禁止。決済・ラベル照合等の別用途のみ許可 |

カタログ上の存在・列型の観測だけでは意味の `confirmed` にしません。Phase 1.2の返還情報のconfirmedは、利用者の仕様・実列の確認結果を根拠とします。Codexによる独立照合ではありません。監査レポートの `catalog_structure_observed` は構造を観測したという意味だけです。

下表のconfirmedは利用者の実列構造確認、needs_confirmationは資料/実DB側の追加確認を示します。形式分類の詳細は [payout_formats.md](payout_formats.md) を参照してください。

| 確認項目 | 現時点の状態 | 候補・未確認事項とコードの動作 |

| cの正式意味 | needs_confirmation | 人気順が候補。2文字だけから順位・特殊コードを確定しない |

| 複数的中・同着 | needs_confirmation | 最大3/5組の構造は保持。複数複勝対象だけで同着と判定しない |

| 不成立・特払・発売なし・中止 | needs_confirmation | それぞれ独立状態。0円・通常払戻・自動返還へ置換しない |
| 訂正/削除・最新版 | needs_confirmation | 正当な最終版・取消の識別・適用順を原仕様/取込仕様で確認。作成日や区分の大小だけで選ばない |

`RawPayoutSlot(a,b,c)` は元の文字列を保持します。`parse_payout_layout()` は通常str・列幅・ASCII数字または指定幅全体のASCII空白・最大組数を検証します。trim・数値化・桁補完をしません。空文字・NULL・不正文字・幅不一致は停止します。

`classify_payout_layout()` は未使用の全空白枠、通常形式候補、00の要確認枠、ゼロ値の要確認枠を分けます。不自然なa/b/cの組合せ、範囲外の馬番候補、通常対象候補の二重登録は停止します。追加対象・枠番号・9桁の先頭ゼロを保持し、同着や対象集合の完全性は推定しません。`format_status=valid` でも `status=needs_confirmation`、`ready_for_settlement=False` です。

`decode_hr_payouts()` は確認ゲートを閉じたままにします。分類の検証後、特殊値または意味・単位の未確認により必ず停止します。全空白だけの場合も発売なし・不的中・0円等にしません。bのint変換や仮の倍率処理はありません。00の意味を解決するフラグ規則や、確認済みと上書きする引数は追加しません。詳細は [settlement_api.md](settlement_api.md)。

### 訂正・削除の採用方針案（proposed）

1. レース6列キー・レコード種別・取込履歴を対応させ、元仕様とPC-KEIBAの上書き/履歴保持方式を確認する。
2. HR1/2の優先・確定後訂正・データ区分0の削除・9の中止との関係を仕様で確定する。同じレースに複数版があれば自動採用しない。
3. 削除は通常不的中や返還を意味しない。削除後の有効版が確定しない間は決済を止める。
4. 訂正時には旧決済の取消/再構築と、ticket_refによる二重計上防止を設計する。最新の作成日時や最大の区分コードを採る代替規則を作らない。

この採用方針は未実装です。仮想APIのrevision_state=finalは架空の正規化契約であり、実HR区分2を自動変換する規則ではありません。

## 区分の参照情報

依頼文では、JV-DataのHR区分は次の意味です。PC-KEIBAで同じコードを保持することの確認は別に必要です。

| コード | 依頼文のJV-Data説明 | 実表対応の状態 |
|---|---|---|
| 0 | 削除 | needs_confirmation |
| 1 | 速報成績（払戻金確定） | needs_confirmation |
| 2 | 成績（月曜） | needs_confirmation |
| 9 | レース中止 | needs_confirmation |

`--payout-status-column` を指定した場合にだけコード別集計を行います。指定しない場合は候補を示し、コードの意味を使う処理を省略します。0～9以外の値は `other`、NULLは `null` に集約し、生値を返しません。HRの3～8は集計には残しますが、この参照情報では意味不明です。

RAの同一キーに複数の異なる区分がある場合は `ra_conflicting_status_races` に集計し、実施/中止の母集団から分離します。HR1と2の併存はレコード存在の確認に留め、どちらのpayloadを採用するかは未実装です。

金額や的中対象を展開していないため「払戻レコード存在」は「損益評価に利用できる」と同義ではありません。NULLキーは集合から分離し、不正な非NULLキーも全体集合と形式正常集合を分けて扱います。年/競馬場のNULLや不正値は年限定の抽出条件外になり得ます。

全期間の年別・収録期間・キー品質は `--include-global-summary` の明示時だけ実行します。正確な件数は索引状態によって全走査になり得ます。通常heap・RLSなし・組み込み型だけを `FROM ONLY` で集計し、既存のタイムアウト・集計行数上限を維持します。

## 特殊ケースと確認手順

通常単勝、通常複勝、単勝同着、複勝同着、返還、中止、不成立、特払、発売なし、欠損、初期値、不正、未対応を別状態で設計します。[backtest_policy.md](backtest_policy.md)にラベルと台帳の扱いを示します。

`payout_policy.py` は将来の実HRに関する方針表で、実フラグを解釈する決済分類器ではありません。Phase 1.2の `refunds.py` は確認済みの28文字と2フラグだけを判定します。Phase 1.3の `settlement.py` は明示した正規化済み架空データだけを決済します。架空テストの成功で未確認のHR変換が確認済みにはなりません。

利用者がローカルで次を確認し、根拠の資料名・版・ページ/項番・実列名・確認日を対応表へ追記します。実レコード・金額・馬IDをこのOneDrive文書に貼り付けません。

1. schema監査でHRの存在・型・PK・索引・監査可否を確認する。
2. 公式仕様と取込仕様で区分・繰返し・単位・初期値・特殊値の対応を確認する。
3. 区分列を明示したキー存在監査を行い、区分差・繰返し・削除の保持方式を確認する。
4. 返還/特払/不成立/発売なしの判別と的中対象集合の対応を確定する。
5. 確認済み規則を用いる実HRの意味変換・決済経路の開放を別途承認する。今回の仮想決済から実DBの損益を計算しない。
